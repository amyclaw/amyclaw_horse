# PRD：MVP 2.0 — 个人助理可共享、按口令鉴权与记忆隔离

## 一、目标与范围

**产品目标**：将当前智能体做成**可共享给所有访问用户使用**的产品——用户只要根据自己名字生成链接即可访问，打开后感受到「这是专门为自己服务的个人 AI 助理」。

**范围**：  
- 不建立用户数据库与密码体系；鉴权仅通过**暗号/口令**。  
- 同一链接（同一 ref/用户名）可能被**不同真实用户**使用，因此需在会话开始时通过口令精确绑定到「某个会话档案」。  
- 支持**主人**与**访客（Guest）**两种使用方式：主人用个人口令；访客用主人设定的「Guest 专用口令」，且主人可控制 agent 对访客公开哪些信息。  
- **记忆与会话严格按会话档案隔离**，并支持同一主人**跨设备**访问同一档案。
- **每位 Guest 独立会话**：同一链接下，每个访客（或每设备/每浏览器首次使用 Guest 口令）拥有独立会话，互不混用；主人可按「访客列表」调阅每条 Guest 会话。

**主人鉴权与 Guest 会话的详细设计**（完善、简洁、鲁棒方案）见 **`docs/MVP2.0_AUTH_DESIGN_OWNER_AND_GUEST.md`**。

本文档为 MVP 2.0 的完整产品与开发计划，与「记忆隔离」相关的技术现状与修复计划已整合在 `GATEWAY_CONFIG_STATUS_MEMORY_ISOLATION.md` 中，此处给出摘要与开发阶段划分。

## 二、记忆隔离（技术前提）

### 2.1 现状结论（详见 GATEWAY_CONFIG_STATUS_MEMORY_ISOLATION.md）

- **会话存储**：按 sessionKey 分文件（`sessions/<uuid>.jsonl` + `sessions.json`），但回复时是否只读当前 session 由 Gateway 实现决定。  
- **长期记忆（memorySearch）**：配置中无按 sessionKey 的 scope/namespace，当前实测存在**跨会话、跨 ref 共享**，新设备/新 ID 可见其他会话内容。  
- **Workspace 文件**：单一份 workspace，所有会话共用，文件级记忆天然跨会话共享。

### 2.2 必须完成的隔离开发（Gateway 侧，MVP 2.0 前置/并行）

| 序号 | 项 | 说明 |
|------|----|------|
| 1 | 会话历史严格按 sessionKey | 回复时拉取、注入的对话历史**仅限当前 sessionKey**，禁止跨 session 读取或注入。 |
| 2 | memorySearch 按 sessionKey 隔离 | 长期记忆的**写入**与**检索**均按 sessionKey（或等价会话 ID）做命名空间/过滤，不向其他 session 返回或注入记忆。 |
| 3 | Workspace 使用策略（可选） | 若继续使用共享 workspace 文件，需明确仅用于「不敏感、可跨会话」的内容；与用户/会话强相关的内容必须进隔离的 session 或 memorySearch。 |

以上为「用户/访客之间互不串会话、不串记忆」的基础，需在 OpenClaw Gateway 应用层实现；配置现状见 `docs/GATEWAY_CONFIG_STATUS_MEMORY_ISOLATION.md`。

## 三、鉴权与会话绑定（无用户库、仅口令）

### 3.1 原则

- **不建用户数据库、不存密码**；身份与会话绑定仅依赖**口令/暗号**。  
- **同一链接（ref）** 可能对应多个「会话档案」（不同人用同一 ref 会生成不同 session，每个 session 绑定一个口令）。  
- 每次会话开始，系统需**先确认当前用户对应哪一个会话档案**，再加载该档案的对话与记忆。

### 3.2 会话开始时的标准流程

1. **默认先询问口令/暗号**  
   用户打开链接（如 `?ref=小明`）后，在进入主对话前，**先由系统/Agent 询问**：「请输入您的口令/暗号以继续」（或类似文案）。

2. **专用鉴权 Agent（或鉴权逻辑）**  
   存在一个**专门负责鉴权的 Agent/模块**，输入为：当前 ref（链接名）+ 用户本次输入的口令。  
   - 在**同一 ref** 下，查询所有已存在的会话档案（session），每个档案在创建时或后续由用户设定并存储了「该档案的口令」（仅存储哈希或加密值，用于匹配，**不对外展示**）。  
   - 用本次输入的口令与各档案的口令做**匹配**（不向用户或 Agent 对话层返回明文口令）。

3. **匹配结果处理**

   - **唯一匹配**：确定当前用户即该会话档案，加载该 session，进入主对话；并支持**跨设备**（同 ref + 同口令即同一档案，任意设备均可访问）。  
   - **多匹配**（同一 ref 下多个档案口令相同，理论上仅巧合或测试）：  
     - 先提示用户：「存在多个档案使用了相同口令，请帮助确认身份。」  
     - 询问：「您曾与助理讨论过哪些话题？」（可列举若干关键词或最近主题）。  
     - 若仍无法唯一确定，则提示：「系统中有多个会话匹配，请选择要开启的档案（按创建时间列出）。」用户选择后进入对应 session。  
   - **无匹配**：  
     - 告知用户：「未找到匹配的档案，我们将为您**开启一个新对话**。您刚才输入的口令/暗号将作为今后在此链接下识别您身份的关键信息。」  
     - 询问：「是否要修改为您更容易记住的暗号/口令？」若用户选择修改，则用新口令创建并绑定新 session；否则用当前输入的口令绑定。  
     - 新会话档案与当前 ref 关联，并持久化「该档案的口令」（仅存储用于匹配的形式，不对外提供）。

4. **鉴权成功后**  
   - 允许用户在该 ref 下**任意跨设备**使用同一档案（只要输入相同口令即可定位到同一 session）。  
   - 前端/后端需保证：同一 ref + 同一口令（匹配到同一 session 档案）时，使用**同一个 sessionKey**（或等价会话 ID），以便 Gateway 侧按 session 隔离对话与记忆。

### 3.3 逻辑完整性补充

- **口令不可被 Agent 输出**：鉴权仅用于「匹配」，Agent 在任何对话中**不得**把用户的口令或暗号以明文形式回复、总结或透露给任何人（包括主人自己若以「请告诉我我的口令」方式问，也应拒绝明文返回；主人查看 guest 的入口见下文「主人调阅」）。  
- **口令存储**：建议仅存哈希或加密值，且仅鉴权模块可做「匹配」判断，其他逻辑不接触明文。  
- **首次访问与「链接名」冲突**：若多人都用同一 ref（如都叫「小明」），则通过**不同口令**区分不同人的档案；同一 ref 下多档案列表（供选择时）可按「创建时间」排序展示。  
- **跨设备一致性**：同一 ref + 同口令 → 同一 sessionKey → 同一会话档案；Gateway 侧已按 sessionKey 隔离后，跨设备访问自然看到同一段对话与记忆。

## 四、访客（Guest）机制

### 4.1 场景

- **主人**：拥有该链接（ref），通过**个人口令**鉴权，使用「个人助理」全部能力。  
- **访客（Guest）**：使用**同一链接**与助理交互，但需使用**主人设定的 Guest 专用口令**，且能力与可见信息受控。

### 4.2 设计要点

1. **Guest 专用口令**  
   - 由**主人**在鉴权通过后设定（可修改），如「访客口令」「会议预约口令」等。  
   - 仅用于「以访客身份」使用该链接；与主人的个人鉴权口令分离。

2. **Guest 可执行的任务（可扩展）**  
   - 例如：**约会议**、**询问事项**（如「主人何时有空」「公司地址」等）。  
   - 具体任务类型可在产品中预定义或由主人在「白名单/权限」中勾选开放。

3. **白名单与信息可见范围**  
   - **主人**通过**白名单机制**授权：Agent 可对「使用 Guest 口令的访客」**公开哪些信息**。  
   - 例如：可公开「本周空闲时段」「公开联系方式」；不可公开「家庭住址」「个人健康」等。  
   - 实现上可在 Agent 的 system/规则中注入「对 Guest 可见主题列表」或「禁止对 Guest 透露的主题列表」，由产品配置或主人设置界面维护。

4. **鉴权口令不对外提供**  
   - Agent **不得**在对话中向任何人（包括主人、Guest）**输出**主人或 Guest 的鉴权口令明文。  
   - 口令只用于「匹配」与「鉴权通过/拒绝」，不用于回答「你的口令是什么」。

5. **主人调阅 Guest 数据**  
   - **主人**鉴权通过后，可**调阅**：  
     - 任意 Guest（使用该链接的 Guest 口令）的**交互记录**；  
     - 以及对应 Guest 的**口令**（用于主人管理/重置，仍建议在管理界面中脱敏展示或仅允许重置而非明文回显，视安全策略而定）。  
   - 实现上需在「主人 session」下提供「查看访客列表 → 选访客 → 看该访客的口令与历史对话」的能力（如管理页或专用指令）。

### 4.3 每位 Guest 独立会话 + 与「同一 ref 多档案」的关系

- **每位 Guest 独立会话**：同一 ref 下，Guest 专用口令是「进入访客通道」的钥匙；**每个访客**（或同一访客在新设备/新浏览器首次用 Guest 口令）对应**一条独立 Guest 子会话**，拥有独立 sessionKey，互不混用。通过「Guest 口令 + guestSessionId」（guestSessionId 由服务端在首次访问时分配并下发给该浏览器）区分不同 Guest；主人调阅时按「访客列表」选择某条 Guest 会话查看其完整对话。详见 **MVP2.0_AUTH_DESIGN_OWNER_AND_GUEST.md**。
- 会话档案分为两类：  
  - **主人档案**：ref + 主人口令 → 一个主人 session（可有多设备，同口令即同 session）。  
  - **Guest 子会话**：ref + Guest 口令 + guestSessionId → 每个 Guest 一条 session，与主人及其他 Guest 隔离；主人仅能「调阅」各 Guest 会话内容，不能在同一对话流中混入。  
- 同一链接下：主人用主人口令；他人用 Guest 口令，每人获得或延续自己的 Guest 会话，仅能看到白名单内信息；记忆与对话按 session 严格隔离。

## 五、界面与体验

### 5.1 从「拜年」到「个人助理」

- **当前**：拜年场景、马厩/马主等话术与 UI。  
- **MVP 2.0**：改为**个人助理**场景，使用户感觉「这是专为自己服务的个人 AI 助理」。

### 5.2 界面修改方向

- **整体风格**：从拜年/节日主题改为**通用个人助理**风格（简洁、专业、可长期使用）。  
- **首屏与引导**：  
  - 用户打开「自己名字的链接」后，首屏应强调「您的个人助理」「为您服务」等，而非节日/马主话术。  
  - 在进入主对话前，先完成**口令询问与鉴权**（见第三节），再进入助理主界面。  
- **UI 提示词与文案**：  
  - 所有面向用户的提示、占位符、按钮文案，统一为「个人助理」语境：如「输入您的口令以进入您的助理」「您的助理已就绪」「与您的助理对话」等。  
  - 避免「马厩」「马主」「拜年」等仅在 MVP 1.0 使用的表述（除非保留为可选主题）。  
  - **具体更改项**（标题、页头、状态文案、占位符、鉴权页、创建链接卡片等）见 **`docs/MVP2.0_FRONTEND_UI_COPY_CHANGELIST.md`**。

### 5.3 体验目标

- 用户**创建自己的链接并打开后**，应明确感知：  
  - 这个链接代表「我的助理」；  
  - 只有我（通过口令）能进入我的对话与记忆；  
  - 我可以把链接给别人用「访客口令」办事（约会议、问事项），而对方看不到我的私人信息。

## 六、开发计划与阶段（整合记忆隔离）

### 6.1 阶段 0：记忆隔离（Gateway 侧，必须先行或与阶段 1 并行）

- **目标**：实现「按 sessionKey 严格隔离」，避免跨会话、跨 ref 串记忆与对话。  
- **任务**：  
  - 会话历史读取与注入仅限当前 sessionKey。  
  - memorySearch 写入与检索按 sessionKey（或等价会话 ID）隔离。  
  - 视需求决定 workspace 与 session 的边界（见 `GATEWAY_CONFIG_STATUS_MEMORY_ISOLATION.md`）。  
- **产出**：Gateway 侧改动、回归测试（含跨设备、跨 ref、新 ID 不可见他人内容）。

### 6.2 阶段 1：鉴权与会话绑定（无用户库、仅口令）

- **目标**：同一链接下通过口令唯一确定或创建「会话档案」，支持跨设备。  
- **任务**：  
  - 设计并实现「会话档案」与「口令」的存储与匹配（哈希/加密，仅匹配不输出）。  
  - 会话开始默认先询问口令；实现鉴权 Agent 或鉴权模块（同 ref 下按口令匹配 session）。  
  - 处理：唯一匹配 / 多匹配（话题消歧 → 按创建时间选档案）/ 无匹配（新对话、确认口令、可选修改）。  
  - 保证同 ref + 同口令 → 同一 sessionKey，跨设备一致。  
- **产出**：鉴权流程、前端首屏「输入口令」与结果分支、后端/Gateway 侧 session 与口令绑定逻辑。

### 6.3 阶段 2：个人助理 UI 与文案

- **目标**：拜年界面改为个人助理界面，文案统一为「专为自己服务的个人助理」。  
- **任务**：  
  - UI 改版（布局、风格、组件）。  
  - 首屏与引导、占位符、按钮、系统提示等文案全部替换为个人助理语境。  
  - 与阶段 1 的「先口令再进主界面」流程衔接。  
- **产出**：新版前端、发布与测试。

### 6.4 阶段 3：访客（Guest）机制

- **目标**：他人使用同一链接时，通过 Guest 专用口令使用受限能力；主人可控制可见信息并调阅 Guest 记录与口令。  
- **任务**：  
  - 主人设定/修改 Guest 专用口令。  
  - Guest 使用链接 + Guest 口令进入「访客会话」；Agent 行为与可见信息受白名单限制。  
  - 实现白名单机制（可对 Guest 公开的主题/信息类型）。  
  - 主人鉴权后可调阅：Guest 列表、某 Guest 的交互记录、该 Guest 的口令（管理用）。  
  - 确保 Agent 从不对外输出任何鉴权口令明文。  
- **产出**：Guest 入口、白名单配置、主人管理界面或指令、策略与安全复核。

### 6.5 阶段 4：联调、测试与文档

- **目标**：端到端验证「隔离 + 鉴权 + 助理体验 + Guest」闭环。  
- **任务**：  
  - 跨设备、同 ref 同口令、多档案消歧、新用户新档案、Guest 白名单与调阅等场景的测试。  
  - 更新用户/运维文档，标注 MVP 2.0 行为与限制。

## 九、开发完成后的功能与体验（综述）

完成上述阶段 0～4 后，产品将具备以下能力与体验：

- **可共享的个人助理**：用户凭「自己名字的链接 + 口令」即可使用，无需注册；打开链接后先输入口令，系统在同一链接下匹配或创建「会话档案」，进入后体验为**专为自己服务的个人 AI 助理**（界面与话术为个人助理风格）。
- **跨设备一致**：同一链接下输入相同口令，任意设备进入同一档案，对话与记忆一致。
- **同一链接多用户**：不同人用同一链接、不同口令，各自拥有独立档案，互不串会话与记忆；多档案同口令时通过话题或按创建时间选档案消歧；无匹配则开新对话并绑定新口令。
- **访客机制**：主人设定 Guest 专用口令并分享链接；他人用 Guest 口令以访客身份使用（如约会议、问事项），助理仅透露白名单内信息；主人可调阅 Guest 交互记录及管理 Guest 口令；鉴权口令仅用于匹配，助理不对外输出。
- **隐私与隔离**：对话与长期记忆按会话档案严格隔离，新设备/新用户无法看到他人内容。

**一句话**：用户通过「自己名字的链接 + 口令」拥有专属个人 AI 助理，无注册、可跨设备、记忆隔离；同一链接可安全交给他人作访客使用（Guest 口令 + 白名单），主人可管理并调阅访客记录，助理从不泄露鉴权口令。更细的逻辑分析、缺陷与补充建议见 **PRD_MVP2.0_PLAN_REVIEW_AND_SUMMARY.md**。
