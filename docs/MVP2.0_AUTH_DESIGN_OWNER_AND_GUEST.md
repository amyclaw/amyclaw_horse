# MVP 2.0：主人鉴权方案 + 每位 Guest 独立会话设计

本文档针对「不用密码、仅用口令」的个人助理系统，给出**主人鉴权**的完善、简洁、鲁棒方案，并明确**每位 Guest 独立会话**的模型与实现要点。可直接纳入 PRD 或作为技术附录。

---

## 一、主人鉴权：完善 · 简洁 · 鲁棒

### 1.1 原则

- **单因素**：仅口令，无账号、无密码、无邮箱/手机绑定。  
- **服务端唯一权威**：口令校验、档案匹配、sessionKey 分配均在服务端完成；前端不持有可伪造的「身份」，仅持鉴权成功后下发的会话绑定信息。  
- **可防暴力、可兜底**：同 ref 下失败次数受限；忘记口令只能开新档案，不提供找回。

**鉴权是否使用数据库？**  
- **不使用「用户数据库」**：不做用户表、账号、密码、邮箱/手机等用户体系；鉴权仅依赖「链接(ref) + 口令」，不建用户库。  
- **档案与鉴权元数据**（ref、档案类型、口令哈希、sessionKey、guestSessionId、创建时间等）需要**持久化**，实现上二选一即可：  
  - **用数据库**（如 SQLite、PostgreSQL）：建「档案/鉴权元数据」表（非用户表），便于按 ref 查档案列表、按 guestSessionId 查 Guest 会话；适合需要按条件查询、列表分页的场景。  
  - **用文件**（如按 ref 分目录的 JSON 文件）：不引入 DB，部署更轻；适合小规模或希望零 DB 依赖的环境。  
- 结论：鉴权**不依赖用户数据库**；档案与口令等元数据**可以**用数据库存（推荐，实现简单），**也可以**只用文件存，由实现选择。

**文件存 vs 数据库存：安全与速度**  
- **安全**：在同等实现下（口令仅存哈希、文件/DB 仅应用进程可读、同机部署），两者安全性相当。关键在：权限收紧（文件 chmod 600 或 DB 专用账号）、不落盘明文、备份与磁盘权限可控。数据库可做连接加密与库级权限，文件可做目录权限与加密盘；任选其一并做足即可。  
- **速度**：鉴权每次仅一次「按 ref + 口令哈希查档案」的查询，数据量小（单 ref 下档案数有限）时，**两者都很快**。数据库带索引时，多档案、多 Guest 时的「查一条/列一页」更稳、扩展更好；单 ref 单文件、文件很小时，读一个 JSON 也足够快。  
- **建议**：小规模或零依赖优先 → 文件存即可；需要按 ref 列档案、分页、多条件查询或后续扩展 → 用数据库（如 SQLite）更省心、更快。

### 1.2 标准流程（简洁）

```
打开链接(?ref=xxx) → 首屏「请输入您的口令」→ 提交 ref + 口令
    → 服务端匹配该 ref 下档案
        → 唯一匹配：返回/绑定该档案的 sessionKey，进入主对话
        → 多匹配：返回档案列表（按创建时间），前端展示「请选择要进入的档案」，用户选后再绑定 sessionKey
        → 无匹配：视为新用户，服务端创建新档案、存储口令哈希、分配新 sessionKey，可选「是否修改口令」再绑定，进入主对话
```

**口令输入方式**：口令必须在**秘密框（密码输入框）**中输入，**不得**在对话输入框里输入。

- **秘密框**：独立于主对话的鉴权页/弹层，使用 `type="password"` 或等效的掩码输入框，输入时以圆点/星号显示，防窥视与截屏泄露。
- **仅提交鉴权接口**：口令只随鉴权请求发给服务端，**不**作为聊天消息发送；鉴权成功后进入主对话，口令**不会**进入会话历史、不会被 Agent 或 Gateway 当作对话内容存储或检索。
- **不用对话框的原因**：若在对话框输入，口令会作为一条「用户消息」进入会话，既会出现在界面历史里，也可能被写入对话日志与长期记忆，增加泄露与误用风险；且无法做输入掩码。故统一采用秘密框 + 独立鉴权流程。

- **跨设备**：任意设备打开同一 ref、输入同一口令 → 匹配到同一档案 → 同一 sessionKey → 同一对话与记忆。无需「记住设备」或额外 token（若后续要做「本设备免输口令」可再加可选长期 token，见 1.4）。

### 1.3 鲁棒性措施

| 措施 | 说明 |
|------|------|
| **口令仅存哈希** | 使用带盐哈希（如 bcrypt/argon2），不可逆；校验时只做「输入 vs 哈希」比对，任何环节不落盘明文。 |
| **同 ref 限速/冷却** | 同一 ref 下连续失败 N 次（如 5 次）后，该 ref 进入冷却（如 5～15 分钟）再允许重试，防暴力枚举口令。可选：按 ref+IP 限速，降低分布式枚举压力。 |
| **口令强度建议（非强制）** | 前端提示「建议至少 4～6 位，避免 123456 等常见组合」；服务端可拒绝明显弱口令（如纯数字 4 位以下），降低撞库风险。 |
| **会话绑定由服务端决定** | 鉴权成功后，由服务端返回「本次会话使用的 sessionKey」或「档案 ID + 服务端签发的短期 token」；前端/horse-server 用其连接 Gateway，不允前端自行构造 sessionKey 访问他人档案。 |
| **Agent 永不输出口令** | 对话层与鉴权层隔离；Agent 在任何回复中不得包含用户口令（含主人、Guest），仅能回答「请通过入口重新输入」等中性话术。 |

### 1.4 可选增强（不改变「仅口令」本质）

- **本设备一段时间内免输口令**：鉴权成功后，服务端签发**长期有效的设备绑定 token**（如 30 天），存于 httpOnly Cookie 或安全存储；下次同设备访问同一 ref 时，先带 token 请求，服务端校验通过则直接返回对应 sessionKey，无需再输口令。若 token 无效或不存在，再走「输入口令」流程。  
- **多匹配时辅助信息**：列表展示档案时，可附带「最近对话时间」或「首条对话摘要」（脱敏），便于用户选择，不依赖自然语言消歧。

### 1.5 忘记口令

- **不提供找回**：无邮箱/手机，无法验证「本人」。  
- **兜底**：用户可在同一 ref 下用**新口令**重新进入「输入口令」流程 → 无匹配 → 系统为其**创建新档案**并绑定新口令；旧档案无法再进入，其对话与记忆仍保留在服务端但不可访问（可选：主人通过 Admin 暗语等极高可信方式申请清理/归档，属运营策略，非 MVP 必选）。

## 二、每位 Guest 独立会话

### 2.1 模型约定

- **Guest 专用口令**：由主人设定，是「进入访客通道」的钥匙；**不区分**具体访客是谁。  
- **每个 Guest 一条独立会话**：同一 ref 下，**每次新访客**（或同一访客在新设备/新浏览器）首次使用 Guest 口令时，系统为其**创建新的 Guest 子会话**，并分配独立的 sessionKey；后续在同一设备/同一浏览器中再次用 Guest 口令访问，可**延续该 Guest 的会话**（通过见下文的 guestToken/guestId 绑定）。

### 2.2 如何区分「每个 Guest」

- **不要求访客注册或登录**，故用「谁第一次用 Guest 口令从哪进来」来区分：  
  - 方案：**Guest 口令 + Guest 会话 ID（guestSessionId）** 共同决定一个会话。  
  - **首次**用 Guest 口令访问（无 guestSessionId）：服务端创建新 Guest 会话、分配 sessionKey 与 guestSessionId，将 **guestSessionId** 通过 Cookie 或前端安全存储（如 localStorage）下发给该浏览器；前端后续请求均带此 guestSessionId，服务端据此定位到该 Guest 的 sessionKey。  
  - **新设备/新浏览器**：无 guestSessionId → 视为新访客，再建新 Guest 会话、新 guestSessionId。  
- **存储关系（服务端）**：  
  - `ref + 主人口令哈希` → 主人档案（ownerArchiveId）→ 主人 sessionKey。  
  - `ref + Guest 口令哈希` → 允许进入访客通道；在此之下：  
    - `ref + guestSessionId` → 该 Guest 的 sessionKey（每个 guestSessionId 对应一个独立会话）。  
  - 主人设定/修改的是「该 ref 的 Guest 口令」；不单独为每个访客设口令。

### 2.3 主人侧：访客列表与调阅

- **访客列表**：按该 ref 下所有 **Guest 子会话** 列表展示（每条对应一个 guestSessionId）；展示项可包含：首次访问时间、最近活动时间、可选「备注名」（主人可编辑，便于识别是谁）。  
- **调阅**：主人选择某条 Guest 记录 → 查看该 **Guest 的完整对话历史**（仅该子会话）；不展示「该访客的口令」（访客无独立口令，只有链接的 Guest 口令；主人可查看/修改的是「当前 Guest 通道口令」）。  
- **安全**：Guest 会话与主人会话、其他 Guest 会话严格按 sessionKey 隔离；主人调阅仅「只读」该 Guest 的会话内容，不在对话流中混入。

### 2.4 与 PRD 的对应

- **「每个 guest 也要有独立的会话」**：采用上述「Guest 口令 + guestSessionId → 独立 sessionKey」模型，每个访客（或每设备/每浏览器首次访客）一条独立会话。  
- **主人鉴权**：采用本文 1.2～1.5 的流程与鲁棒性措施，保持**完善、简洁、鲁棒**；实现时以服务端为唯一权威，口令仅哈希、限速、可选强度建议与可选「本设备免输口令」。

## 三、实现层级建议（不变）

- **鉴权与档案存储**：horse-server 或独立鉴权服务；维护 ref、档案类型（主人/访客）、口令哈希、sessionKey、guestSessionId 等。  
- **会话与 Gateway**：鉴权成功后，由该服务决定并返回 sessionKey（或 token 对应 sessionKey）；前端或 horse-server 使用该 sessionKey 连接 Gateway，保证「一档案一会话、会话隔离」。  
- **Guest 会话创建**：在「Guest 口令校验通过且当前请求无有效 guestSessionId」时，创建新 Guest 会话、分配 guestSessionId 与 sessionKey，并下发给前端。

此设计可直接作为 PRD 中「主人鉴权」与「Guest 独立会话」的定稿方案，用于阶段 1、阶段 3 的开发与验收。
