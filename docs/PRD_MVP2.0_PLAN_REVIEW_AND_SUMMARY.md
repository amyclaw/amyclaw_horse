# MVP 2.0 开发计划：逻辑分析、缺陷与补充 + 完成后功能与体验综述

## 一、逻辑合理性总体评价

整体目标清晰（可共享个人助理、无用户库仅口令、同一链接多用户、Guest 机制），阶段划分（隔离 → 鉴权 → UI → Guest → 联调）顺序基本合理，**阶段 0 必须先行**的依赖正确。以下为逐项逻辑检查、不合理/缺陷与建议补充。

---

## 二、不合理与缺陷分析

### 2.1 会话档案与 sessionKey 的生成与绑定（实现模糊）

**问题**：PRD 要求「同一 ref + 同口令 → 同一 sessionKey」，但未说明：

- sessionKey（或等价会话 ID）**由谁生成、何时生成**：前端、horse-server 还是 Gateway？
- 当前实现中 sessionKey = `agent:main:horse_<ref>_<uid前8位>`，其中 uid 来自前端 localStorage，**与口令无关**；若不做改动，无法实现「输口令 → 定位到已有档案的 session」。

**结论**：逻辑上需要「先鉴权、再定 session」：用户先提交 ref + 口令，**服务端**匹配到某档案后，用**该档案对应的 sessionKey** 去连 Gateway；新用户则服务端创建新档案并分配新 sessionKey，再让前端用该 sessionKey 建立会话。  
**补充建议**：在 PRD 或技术方案中明确：（1）「档案」与 sessionKey 一一对应；（2）档案与口令的存储与匹配在**服务端**（horse-server 或独立鉴权服务）；（3）前端在鉴权成功前**不**自定 sessionKey，鉴权成功后由服务端返回或重定向到带正确 sessionKey 的连接方式。

---

### 2.2 Guest 会话的粒度与主人调阅对象

**问题**：

- 若「Guest 专用口令」只有**一个**，且所有访客共用该口令，则要么所有人进**同一个 Guest 会话**（对话混在一起），要么需要额外维度区分访客（如每次新设备一个会话），PRD 未明确。
- 主人「调阅任意 Guest 的口令与交互记录」：若多访客共用一个 Guest 口令、一个会话，则不存在「某个 Guest 的口令」——只有「该链接的 Guest 口令」；调阅的则是「所有使用该 Guest 口令的对话」，无法按人区分。

**结论**：需要约定 Guest 的会话模型。  
**补充建议**（二选一或组合）：  
- **方案 A**：一个 ref 下**仅一个 Guest 会话**（一个 Guest 口令），所有访客共享该会话；主人调阅的是「该 Guest 会话的完整记录」，不区分「哪个访客」。适合「公共预约/询问入口」场景。  
- **方案 B**：Guest 口令是「访客通道」的钥匙，但**每个访客首次用该口令进入时**为其创建**独立 Guest 子会话**（如用 guest_<ref>_<临时ID>），主人可调阅「访客列表（按首次访问时间或匿名 ID）」及每个子会话的记录；Guest 口令本身由主人设定且可修改，主人可查看「当前 Guest 口令」而非每个访客的口令（因访客无独立口令）。  
在 PRD 中明确采用哪种方案，并据此写清「主人调阅」的对象（整段 Guest 对话 vs 按访客子会话列表）。

---

### 2.3 「主人」的定义与同一 ref 下多主人档案

**问题**：同一 ref（如「小明」）可能被多人使用，每人设不同口令，形成多个「主人档案」。PRD 未定义：

- 是否存在**唯一「链接拥有者」**（即主人）概念，还是「每个档案都是自己的主人」？
- 若存在唯一主人，则需约定**谁算主人**（例如该 ref 下第一个创建的档案、或需单独「认领」动作）；否则「主人设定 Guest 口令」「主人调阅 Guest」中的「主人」无法对应到具体档案。

**补充建议**：  
- 约定：**同一 ref 下第一个创建的会话档案**视为该链接的**主人档案**（或：创建时用户选择「以主人身份使用」则标记为主人档案）；仅主人档案可设定 Guest 口令、管理白名单、调阅 Guest。  
- 或明确：**每个档案都是对等「主人」**，但仅「第一个档案」或「标记为主人的档案」拥有 Guest 管理权；其余同 ref 档案仅为「个人使用」。在 PRD 中二选一并写清。

---

### 2.4 多匹配消歧的可行性与优先级

**问题**：「您曾与助理讨论过哪些话题？」依赖系统能根据**该档案**的历史生成话题摘要，并与用户回答做匹配。实现成本高且容易误判（多个档案都聊过「工作」）。

**补充建议**：  
- **优先**采用「多匹配时直接按创建时间列出档案，用户选择要进入的档案」（PRD 已有），保证可落地。  
- 「话题消歧」作为**可选增强**：若某档案有最近几条对话的简短摘要（如首句或标题），可展示给用户做辅助选择，而不依赖自然语言理解。  
- 在阶段 1 任务中写清：多匹配时**必须**支持「按创建时间选档案」；话题消歧为可选或后续迭代。

---

### 2.5 鉴权与 session 绑定的实现层级

**问题**：口令存储、匹配、以及「匹配后使用哪个 sessionKey」由哪一层实现未写清。若 Gateway 不开放「按 ref+口令返回 sessionKey」的 API，则必须在 Gateway 上游（horse-server 或新服务）维护「ref + 档案 ↔ sessionKey」的映射，并在鉴权成功后代替前端用指定 sessionKey 连接 Gateway。

**补充建议**：在 PRD 或技术方案中增加「实现层级」说明：  
- 口令与档案的**存储与匹配**：horse-server 或独立鉴权服务（推荐，便于与现有 horse-server 集成）。  
- **Session 绑定**：鉴权服务维护「ref + 档案ID → sessionKey」；前端与 Gateway 的连接经 horse-server 转发时，由 horse-server 根据鉴权结果注入或选择 sessionKey。  
- 明确 Gateway 是否需要配合（例如支持「由上游指定 sessionKey」的 connect/chat 接口）。

---

### 2.6 忘记口令与安全策略

**问题**：  
- 用户**忘记口令**时无找回机制，PRD 未提。  
- 口令若过短或简单，存在被暴力尝试的风险。

**补充建议**：  
- **忘记口令**：明确「不支持找回；用户可在此 ref 下用新口令开启**新对话档案**，旧档案无法再进入」（或注明：未来可考虑主人通过 Admin 暗语等极高可信方式重置，MVP 2.0 不承诺）。  
- **安全**：建议口令最小长度（如 4～6 字符）与「同一 ref 下连续失败 N 次后冷却」写入非功能需求或安全附录，阶段 1 实现时落实。

---

### 2.7 Guest 白名单的实现粒度

**问题**：白名单「可对 Guest 公开哪些信息」若仅靠自然语言描述（如「可公开本周空闲时段」），Agent 容易越界或遗漏，需要可执行的边界。

**补充建议**：  
- 白名单采用**主题/类型 + 示例**：如「可公开：日程空闲时段、公司地址、公开联系方式；禁止：家庭住址、健康、财务详情」。  
- 在 Agent 的 system/规则中**显式注入**「当前为 Guest 模式；仅可回答以下主题：…；禁止透露：…」，并在阶段 3 设计「主人配置界面」时定义可选的预设主题与禁止项，便于实现与审计。

## 四、开发完成后的功能与用户体验综述

### 4.1 功能概览

- **个人助理可共享**  
  任何人可通过「以自己名字（或任意标识）生成的链接」访问同一个产品；打开链接后，通过**口令**进入「自己的」或「新的」对话档案，体验为**专为自己服务的个人 AI 助理**。

- **无账号体系、仅口令鉴权**  
  不建用户库、不存密码；身份完全由**暗号/口令**绑定到「会话档案」。同一链接可被多人使用，每人用不同口令拥有独立档案；**跨设备**时，只要在同一链接下输入相同口令，即进入同一档案、看到同一对话与记忆。

- **会话开始必先验证身份**  
  每次打开链接，先被要求输入口令；系统在**该链接下**查找匹配的档案：  
  - **唯一匹配** → 直接进入该档案的助理对话；  
  - **多匹配**（极少）→ 通过「曾讨论话题」或**按创建时间选择档案**确认身份后进入；  
  - **无匹配** → 提示将开新对话，当前输入的口令将作为今后身份凭证，并可选择是否修改后再绑定；绑定后进入新档案。

- **个人助理界面与话术**  
  界面从「拜年/马厩」改为**个人助理**风格：简洁、通用、长期可用；首屏与文案强调「您的个人助理」「为您服务」；用户明确感到「这是专为我服务的 AI 助理」。

- **访客（Guest）使用同一链接**  
  主人可设定**Guest 专用口令**并分享链接；他人使用该链接时输入 Guest 口令，以**访客身份**与助理交互，可做限定任务（如约会议、询问事项）；助理对访客**仅能透露主人白名单内的信息**（如空闲时段、公开联系方式），不透露私人敏感信息。  
  主人鉴权后，可**调阅**使用该链接的 Guest 的**交互记录**（及在采用「访客子会话」模型时按访客维度的记录）；可查看或管理 Guest 口令（如重置），但**助理在对话中从不向任何人输出鉴权口令**。

- **隐私与隔离**  
  对话与长期记忆**严格按会话档案隔离**：不同档案、不同 ref、不同设备（不同口令）之间**互不可见**；新设备、新用户无法看到他人对话或记忆。

### 4.2 典型用户旅程（开发完成后）

**场景 A：首次使用、创建自己的助理链接**

1. 用户打开产品，输入或选择自己的名字（如「小明」），得到链接 `…?ref=小明`。  
2. 打开链接 → 首屏为「您的个人助理」风格，提示输入口令以继续。  
3. 用户输入口令（如「我的暗号 123」）→ 无匹配 → 系统提示将开新对话，该口令将作为今后身份认证依据，并询问是否修改。  
4. 用户确认或修改后 → 进入**小明**的**个人助理**主界面，可正常对话；之后在同一链接下、任意设备输入同一口令，都会进入同一档案、看到同一历史。

**场景 B：老用户换设备**

1. 用户在手机打开 `…?ref=小明`。  
2. 输入与电脑上相同的口令 → 唯一匹配 → 直接进入与电脑一致的对话与记忆，无需注册或登录。

**场景 C：他人用同一链接（访客）**

1. 主人「小明」把链接和 Guest 口令（如「预约」）发给同事。  
2. 同事打开链接，输入 Guest 口令「预约」→ 以访客身份进入，可问「小明本周何时有空」「公司地址」等；助理仅回答白名单内信息。  
3. 小明在自己设备用主人口令进入后，可在「访客管理」中查看该 Guest 会话（或按访客维度的记录）及当前 Guest 口令设置。

**场景 D：同一链接、不同人（多档案）**

1. 另一人也打开 `…?ref=小明`（同名或误用链接）。  
2. 输入自己的口令 → 无匹配 → 系统提示开新对话并绑定该口令；该用户得到**独立于小明**的另一个档案，两人对话与记忆完全隔离。

### 4.3 体验总结（一句话）

**开发完成后**：用户通过「自己名字的链接 + 口令」即可拥有**专属于自己的个人 AI 助理**，无注册、可跨设备、对话与记忆严格隔离；同一链接可安全地交给他人作为访客使用（Guest 口令 + 白名单），主人可管理访客权限并调阅访客记录，且助理从不泄露任何人的鉴权口令。
